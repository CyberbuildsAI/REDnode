REDnode

REDnode is a Node-based API for scripting Cyberpunk 2077, built on the same injection points that RED4ext, Cyber Engine Tweaks and redscript already use. Asynchronous mods run in a normal Node process. A small sandboxed tier runs inside the game for the few cases that must change a value mid-call.

Recommended: hybrid B + small A Tier 2: Node (out of process) Tier 1: sandboxed in-process Single-player modding

01Goal and scope

In scope
  • Let modders write game logic in TypeScript and JavaScript with npm packages.
  • Expose game state, events and commands through a typed API generated from the game's own reflection data.
  • Coexist with CET, RED4ext plugins, redscript and REDmod.
  • Survive game patches without per-patch rewrites of mods.
Out of scope for v1
  • Multiplayer or anything that touches online services.
  • Full in-process Node with fs, require and a live event loop.
  • Replacing redscript for engine-level changes.
  • Mods that need to run arbitrary game calls from inside a hook.

What this teaches

  • The game exposes a reflection (RTTI) system. That is what makes a dynamic scripting layer possible, and CET relies on it.
  • Codeware is a native RED4ext plugin that exposes extra functions to redscript. A native bridge exposing a scripting surface is the established pattern.
  • RedData and mod_settings ship a native DLL together with .reds files. Mod authors already expect that packaging shape.

The tradeoff in Plan B

A hook runs inside the game's own function call, on the game thread, and the game waits for it to return. If the logic lives in another process, the hook must block on a round trip. That costs roughly 50 to 200 µs when healthy and much more when Node is busy. A 60 fps frame has about 16 ms, and hooks such as damage or per-frame ticks can fire thousands of times a frame. If the Node process crashes or hangs, the game thread blocks until a timeout.

PatternPlan B
Notify: "the player took damage"Works. The hook enqueues an event and returns.
Query: "what is the player's health?"Works. Node awaits the answer.
Command: "set health to 100"Works. Queued and applied on the game thread next tick.
Intercept: change a value before the call continuesDoes not work well. Needs a synchronous answer while the game waits.

04Recommended design: two tiers

Keep Plan B as the main path. Add a small in-process tier for interceptors only. A mod can ship either tier or both.

NATIVE PLUGIN ⇄ NODE · named pipe or local socket · events out, queries and commands in · interceptor parameters pushed ahead of time
Tier 1 · sync interceptors
  • Runs inside the hook on the game thread.
  • Can change arguments or return values, or cancel a call.
  • No await, no I/O, no require.
  • Hard time budget, for example 100 µs.
Tier 2 · async Node mods
  • Observe events, query state, send commands.
  • Full Node and npm.
  • Never blocks the game.
  • Can push parameters to Tier 1 interceptors.

Tier 1 shares TypeScript types with Tier 2 but is not Node. The documentation must say so plainly.

Cheaper than either: declarative rules

For the simplest cases, such as "multiply incoming damage by X", offer a no-code rule that the native plugin applies directly in the hook. It needs no JS engine and no IPC, and it covers a large share of real mods.

05API sketch

Tier 1 · interceptor (sync, sandboxed)
export default defineInterceptor({
  target: "PlayerPuppet.OnDamageReceived",
  run(ctx) {
    ctx.args.damage *= ctx.params.multiplier;   // pushed from Tier 2
  }
});
Tier 2 · async mod (full Node)
import { game } from "rednode";

game.on("PlayerPuppet.OnDamageReceived", async (e) => {
  await db.log(e);                          // fine, the game is not waiting
  game.player.setHealth(100);              // queued, runs next tick
});

const hp = await game.player.getHealth();    // async query
interceptor("damage-scale").set("multiplier", 0.5);

Native plugin responsibilities

  • Enumerate RTTI classes, functions and properties for type generation.
  • Call functions and get or set properties on game objects.
  • Hook functions through RED4ext and the Address Library so mods survive patches.
  • Marshal game types (CName, Vector4, handles, arrays) to and from JSON-like values.
  • Queue all incoming commands and run them on the game thread, because game objects are not thread-safe.
  • Manage object handle lifetime so Node never holds a stale reference.

06Safety rails for Tier 1

Hard requirement

A buggy interceptor must never crash or freeze the game.

Time budget

Each call is time-limited. On overrun, return to default game behavior.

Fault handling

Catch exceptions, fall back to defaults, and auto-disable an interceptor after repeated failures.

Ordering

Define priority and chaining when several mods hook the same function.

Typed writes

Validate every write to ctx.args against the real parameter types before it reaches the game.

Limited host API

Read-only accessors and shared-memory reads only. No arbitrary game calls from a hook, to avoid reentrancy bugs.

Safe reload

Swap Tier 1 code between frames. Tier 2 reloads freely.

08Roadmap

P0RESEARCH

Map the ABI

Read the RED4ext plugin entry points and the imports and exports of an installed plugin. Inspect how cyber_engine_tweaks.asi hooks and resolves addresses.

P1PROOF

Hello-world plugin

A RED4ext plugin that logs the RTTI class count. Confirms build, load and logging on the current game version.

P2TIER 2

Pipe bridge and Node SDK

Expose one function over a named pipe and call it from Node. Then events, queries, commands and generated types.

P3RULES

Declarative rules

Native fast-path rules applied inside hooks with no IPC. Gives synchronous behavior with no engine.

P4TIER 1

QuickJS interceptors

Add the sandboxed runner, time limits, ordering and fault handling. Only after P2 and P3 show which hooks need it.

09Open questions

  • Full CET-style reflection access, or a smaller curated API for v1?
  • Which hooks must support Tier 1 interception on day one?
  • Implementation language for the native plugin: C++ with RED4ext.SDK, or Rust with red4ext-rs (Audioware is a Rust precedent)?
  • IPC transport: named pipe, local socket, or shared memory for hot data?
  • Packaging: should a Node mod ship inside the usual red4ext/plugins layout or its own folder?
